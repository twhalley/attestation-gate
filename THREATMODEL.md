# Threat model

The gate in this repository answers exactly one question at admission time:

> Was this specific image digest signed, and attested as built, by the one
> workflow identity we have decided to trust — and is that signature in a
> public transparency log?

Everything below follows from the fact that this is the *only* question it
answers. A control that is oversold is worse than one that is understood, so
the "does not stop" section is the longer one, and deliberately so.

---

## Trust anchors

| Anchor | What it is | What happens if it is wrong |
|---|---|---|
| Fulcio root | Sigstore's public CA (`fulcio.sigstore.dev`) | An attacker who controls it can mint a certificate for any identity. Every signature check becomes meaningless. |
| Rekor log | Sigstore's public transparency log (`rekor.sigstore.dev`) | Signatures could be backdated or hidden. Detection, not prevention, is lost. |
| GitHub OIDC issuer | `token.actions.githubusercontent.com` | An attacker who can mint tokens for our repo can obtain a valid signing certificate. |
| Workflow identity | `.../build-sign-attest.yml@refs/heads/main` | Anyone who can change that file on `main` can change what gets signed. |

Note that the last row is not a Sigstore problem. It is the load-bearing one.

---

## What this stops

**A compromised or unauthorised pipeline pushing to the same registry.**
`untrusted-signer.yml` is the demonstration. It has `packages: write` and
`id-token: write`, it signs correctly, it attests correctly, its signature is
genuinely in Rekor — and it is rejected, because Fulcio binds the certificate
to *that workflow's* identity. Test case `rogue`.

**An image pushed straight to the registry by a human with a PAT.**
No OIDC certificate, so no signature the policy accepts. Test case `unsigned`.

**A tag being repointed at a different image.** Signatures bind to digests, not
tags. Repointing `:trusted` at another image does not carry the signature over;
the webhook resolves the tag to a digest at admission and the new digest has no
valid signature.

**Signing that leaves no public record.** The `ctlog` requirement means a
signature that was never logged is rejected, so an attacker who obtains signing
capability cannot use it quietly. Test case `keysigned`.

**A signature without a build story.** Requiring the provenance attestation
separately means "something signed this" is not sufficient; the artefact has to
come with a claim about how it was built. Test case `no-provenance`.

**Images nobody wrote a policy for.** `no-match-policy: deny` in `test/setup.sh`.
Without it, pushing to an unmatched registry path bypasses the gate entirely.

**A container escalating once it is running.** Pod Security Admission
(`restricted`) is enforced on the same namespace: non-root, no privilege
escalation, all capabilities dropped, seccomp `RuntimeDefault`, no host
namespaces or `hostPath`. This is a separate control answering a separate
question, and it would still apply to an image that somehow satisfied the
signature policy.

**A build that silently changed underneath a signature.** Dependencies are
pinned exactly in `requirements.txt`, so the artefact that was scanned and the
artefact that was signed contain the same package versions.

## What this does not stop

**A malicious commit on `main`.** This is the big one, and it is inherent, not a
gap in the implementation. If an attacker lands a commit — via a compromised
maintainer account, a review bypass, or a malicious dependency update — the
release workflow will build it, sign it, attest it, and the gate will admit it,
correctly. The signature proves *provenance*, not *good intent*. Source
integrity is a different control: branch protection, required review, commit
signing.

**A compromised build step.** The provenance here is generated by the same job
that builds the artefact, so a malicious action or a compromised base image in
the build stage can influence both. This is roughly SLSA Build L2, not L3:
the provenance is authenticated, but it is **not non-falsifiable**, because
the build process could forge its own predicate. Reaching L3 means moving
generation into an isolated builder the build steps cannot reach — the
`slsa-github-generator` reusable workflow, or an equivalent hosted builder.
I chose not to claim L3 rather than claim it loosely.

**A vulnerable dependency.** Nothing here scans at admission, and the gate would
happily admit a signed image full of critical CVEs. `scan-diff` measures; it
does not enforce. Wiring a severity threshold into admission is a deliberate
omission — blocking on CVE count without reachability analysis mostly produces
alert fatigue and pressure to add exceptions.

**A compromised package index.** `requirements.txt` pins versions but not
hashes. A compromised PyPI mirror, or an account takeover that re-uploads a
wheel under an existing version, would be installed and then faithfully signed.
`pip install --require-hashes` pins the artefact rather than the version number
and closes this; it is not done here, and the gap is more real than most people
assume, because the pipeline would attest to the result without complaint.

**Dependency confusion.** Nothing here pins an index or verifies package
provenance, so a package resolved from an unexpected source would be built and
signed like any other. This is the attack that VEX and SBOMs describe after the
fact but do not prevent.

**Runtime compromise.** Admission is a one-time check at Pod creation. Nothing
here observes the workload afterwards.

**A malicious base image that is correctly signed.** The policy trusts our
workflow, and our workflow trusts `cgr.dev/chainguard/*`. That trust is
transitive and unverified — the build does not itself verify the base image's
signature before using it. A real deployment should, and that is the most
obvious next control to add.

**Namespace-scoped enforcement bypass.** Enforcement is opt-in via the
`policy.sigstore.dev/include: "true"` label. Anyone who can create a namespace
without that label, or remove it from an existing one, has an unenforced place
to run whatever they like. In production this needs a second control — a
policy that governs namespace labels themselves.

**Availability coupling.** The gate depends on public Fulcio and Rekor being
reachable. `mode: enforce` means an outage fails closed and blocks deploys.
That is the correct default, and it is a real operational trade-off to have
made consciously rather than by accident.

---

## Residual risk, stated plainly

The strongest honest claim this repository supports is:

> Only artefacts produced by a specific, publicly auditable GitHub Actions
> workflow, from this repository's `main` branch, can run in the `gated`
> namespace.

It does **not** claim the artefacts are safe. It moves the question from
"do I trust this binary?" to "do I trust this repository and its release
path?" — which is a smaller, more answerable question, and that is the entire
value of the control.
